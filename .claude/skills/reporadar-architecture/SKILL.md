# RepoRadar architecture conventions

RepoRadar is a portfolio app: every pattern in it is there to show one Next.js
feature cleanly. Keep it that way. Prefer the pattern already used in the repo
over a new one, and when two patterns coexist on purpose (see "Deliberate
duplicates"), keep both.

`docs/ARCHITECTURE.md` is the long-form explanation; this file is the rulebook.
If they disagree, the code wins, then fix the doc.

## 0. Before writing code

- This is Next.js 16.4 with `cacheComponents: true` and `partialPrefetching: true`.
  APIs differ from older Next. Check `node_modules/next/dist/docs/` for any API
  you are not sure about (AGENTS.md requires this). Never use `middleware.ts`,
  `export const revalidate`, `export const dynamic`, `unstable_cache` or
  `fetch(..., { next: { revalidate } })`: they are the pre-Cache-Components way.
- Package manager is pnpm, Node 22 (`.nvmrc`). Path alias `@/*` → `src/*`.

## 1. Folder and module boundaries

The layout (`app → features → entities → shared`), feature anatomy and
import rules are defined in **reporadar-principles** (migrated in M8). Where
things live:

| What | Where |
| --- | --- |
| GitHub client, cached getters, tags, types, catalogs, search constants, repo-name checks, `RepoCard` | `entities/github/*` (client-safe `@/entities/github`, server entry `@/entities/github/server`) |
| `Skeleton`, `Stat`, `Modal`, `UpdatedAt`, `OgCard` | `shared/ui/*` |
| `format`, `get-query-client`, `get-json`; `use-hydrated`, `use-in-view` | `shared/lib/*`, `shared/hooks/*` |
| Public URL, reserved segments; server secrets | `shared/config/site.ts`; `shared/config/env.ts` (server-only, ADR 0005) |
| Query keys and options | the owning feature's `queries.ts` (`search`, `repo`, `watchlist`) |
| Cookie storage, Server Actions, watch buttons, `/watchlist` body | `features/watchlist/*` |
| Search view, result card, prefetch, preview modal body | `features/search/*` |
| Repo page body and its streamed sections | `features/repo/*` |
| Trending, leaderboard, field and profile page bodies | `features/{trending,leaderboard,fields,user}/*` |
| Providers, SiteHeader | `app/_components/*` |

Module rules:

- The GitHub client, cached getters and watchlist storage start with
  `import "server-only"`. Anything that reads secrets (via `env.*`) or `cookies()`
  must too.
- Client Components never import a server-only module or a barrel that
  re-exports one. Client-safe types and catalogs have their own entry point.
- Static lookup tables (`TRENDING_RANGES`, `LANGUAGES`, `SEARCH_SORTS`) are `as const`
  objects with a derived key type and an `isX(value): value is X` guard using
  `Object.hasOwn`. Follow that shape for new ones.

## 2. Naming

- Files and folders: kebab-case (`search-result-card.tsx`, `use-in-view.ts`).
  Next special files keep their names (`page.tsx`, `loading.tsx`, `opengraph-image.tsx`).
- Components: PascalCase named exports. Only Next special files use `export default`.
- Hooks: `useX` in `use-x.ts` (shared ones in `shared/hooks`).
- Data functions: `getX` for cached reads in the GitHub entity, verb-first for actions
  (`setWatched`, `removeFromWatchlist`).
- Query helpers: `xQueryOptions()` / `xInfiniteOptions()`; keys only via the feature's `xQueryKey` (`searchQueryKey`, `repoQueryKey`, `watchlistQueryKey`).
- Cache tags only via `tags.*` in the GitHub entity, lowercase, `kind:id` form.
- Skeletons: `XSkeleton` exported from the same file as `X`.
- Page props: `type Props = PageProps<"/route/[param]">` (generated by `next typegen`).

## 3. Server vs Client Components

- Default is a Server Component. Add `"use client"` only for state, effects, event
  handlers, browser APIs or TanStack hooks. Keep client components as small leaves.
- Server Components fetch data by calling the GitHub entity's server API directly. They never call
  our own `/api/*` routes.
- Pass only serializable props across the boundary. Server content goes into client
  wrappers as `children` (see `Providers` in `app/layout.tsx`).
- `error.tsx` is always a Client Component.
- UI that depends on browser-only data (client cache, time, storage) renders the
  server version first via `useHydrated()` to avoid hydration attribute mismatches.
- Pages kept alive by `<Activity>`: effects that open/close things (like `<dialog>`)
  must be symmetric, set up in the effect and torn down in cleanup.

## 4. Data fetching, caching and ISR

- Every cached read lives in the GitHub entity (`entities/github/cached.ts`, exported from `@/entities/github/server`) and has, in order:
  `"use cache"`, `cacheLife(...)`, `cacheTag(...)` (except search, which is not tagged).
  Current lifetimes: repo/readme/user `hours`, languages/contributors/leaderboard/field
  `days`, trending `hours`, search `minutes`. Keep a new function consistent with its
  neighbours and add it to the table in ARCHITECTURE.md §6.
- `githubJson` / `githubText` return `null` on 404 and throw `GitHubError` /
  `GitHubRateLimitError` otherwise. Pages turn `null` into `notFound()`; errors go to
  `error.tsx`. Don't catch errors in pages unless degrading one item (as `/watchlist` does).
- Search endpoints are serialized in the client (`/search/*` queue). Do not add
  concurrency to search requests, and keep `generateStaticParams` lists small
  (GitHub's secondary rate limit breaks the build).
- `params` and `searchParams` are Promises. Pages pass them unawaited into a child
  inside `<Suspense>` and await there, so the static shell stays generic.
  (`u/[login]` deliberately awaits at the top and relies on `loading.tsx`.)
- Run independent reads with `Promise.all`.
- Anything per-request (`cookies()`, search params data, `dehydrate()`) sits inside
  `<Suspense>`; call `await connection()` before using TanStack `dehydrate()`.
- `generateMetadata` reuses the same cached `getX` as the page; no extra fetches.
- On-demand invalidation goes through `POST /api/revalidate` with `revalidateTag(tag, "max")`.
  A new tag kind must be added to both `tags` and `TAG_PATTERN`.

## 5. TanStack Query

Use it only for data that changes after load without navigation (search typing,
infinite scroll, hover prefetch, preview modal, watchlist state). Server-rendered
pages don't need it.

- `getQueryClient()` is the only way to get a client: fresh per request on the
  server, a singleton in the browser. Never `new QueryClient()` elsewhere.
- Keys and options live in the owning feature's `queries.ts` and are shared by server and client.
  Server prefetch spreads the shared options and overrides only `queryFn` to call
  the GitHub entity directly.
- Client `queryFn`s go through `getJson` to our Route Handlers and pass `signal`.
- Search params are normalized with `parseSearchParams` on both sides so keys match.
- Hand data to the client with `<HydrationBoundary state={dehydrate(queryClient)}>`.
- Optimistic writes: TanStack `onMutate` (cancel, snapshot, set) + `onError` rollback
  + `onSuccess` store server value, when the truth lives in the client cache.
  `useOptimistic` + `<form action>` when the truth is server-rendered props.

## 6. Mutations: Server Actions and Route Handlers

- Browser writes use Server Actions in `features/<x>/actions.ts`. Treat every argument as
  untrusted: validate, cap sizes, and return `{ ok: false, error }` instead of throwing.
- Cookies are written only in Server Actions or Route Handlers, through the helper
  module that owns them (`features/watchlist/storage.ts`).
- Route Handlers exist only for browser reads that need a secret/httpOnly cookie,
  and for outside callers. They return `Response.json`, map `GitHubError` to its
  status, and validate input (secrets compared with `timingSafeEqual`).

## 7. Routing features

- `src/proxy.ts` is for cheap URL decisions only: redirects (308) and rewrites on
  GET/HEAD, response headers. No data fetching. Reserved first segments live in
  `RESERVED_SEGMENTS` (`shared/config/site.ts`); a new top-level route must be added there.
  Any new top-level metadata route or static asset must be excluded in `matcher`.
- Preview modal: `search/@modal` slot with `(..)[owner]/[repo]`, plus `default.tsx`
  and `page.tsx` returning `null`. The modal's "Open full page" stays a plain `<a>`.
- Use `<Link>` for internal links and `next/form` for GET search forms.
- OG images use `ImageResponse` with inline styles (no Tailwind) via `shared/ui/og-card.tsx`.

## 8. Styling

Tailwind v4 utility classes inline, zinc palette, `dark:` variants on every
coloured surface. `next/image` for avatars (host allowed in `next.config.ts`).

Formatting is Biome's job (ADR 0007): run `pnpm format` before handing work
over and never hand-format against it. Biome only formats; lint rules live in
ESLint. Tailwind class order is not enforced.

## 9. Testing expectations

- Unit tests (Vitest, Node env) sit next to the code as `*.test.ts`, for logic in
  `entities/**`, pure feature modules and `proxy.ts`. Mock `fetch` with `vi.stubGlobal`, `next/headers` and `next/cache` with
  `vi.mock`, env with `vi.stubEnv`; no network. `server-only` is aliased to an empty module.
- New pure logic (parsing, validation, paging, URL rules) gets unit tests.
  Coverage floor (ADR 0006): 80% of lines across `src/entities/**`, `src/proxy.ts`
  and pure feature modules; `.tsx`, re-export entry files, Server Actions and
  Route Handlers are excluded. `pnpm test` enforces it (`vitest.config.mts`).
  Don't lower it without a new ADR. React
  components are covered by Playwright, not unit tests.
- Smoke tests (`e2e/smoke.spec.ts`, Playwright) run against `pnpm build && pnpm start`
  on port 3100 with the real GitHub API, one worker. A new user-visible feature gets
  one smoke test; select by role/text, not by CSS classes, where possible.
- CI (`.github/workflows/ci.yml`) runs lint, typecheck, unit tests, then build + e2e.
  Everything must pass locally before asking Oleg to commit.

## 10. Deliberate duplicates (do not "clean up")

- Two optimistic patterns: `WatchButton` (TanStack) and `WatchlistItems` (`useOptimistic`).
- Two loading styles: inline `<Suspense>` (repo, trending, search) and `loading.tsx` (`u/[login]`).
- Explanatory comments describing the Next.js feature in use. They are part of the showcase.

## 11. Working rules

- Structural decisions live in `docs/adr/`. A change that contradicts one needs
  a new ADR first; propose it to Oleg.

- Never commit, push, open PRs or deploy without Oleg's explicit go-ahead.
- After a milestone, update `docs/ARCHITECTURE.md` and `docs/PLAN.md`.
